**6. AI Classification**

**Important Correction**
Your four requested labels should remain in the interface, but they should not be treated as a simple confidence ladder.

**“Mixed-use” describes workload composition, not lower certainty.**

Maintain three separate concepts:

1. Public classification.
2. Evidence strength.
3. Deployment stage.

**Classification Rubric**

| Category | Required evidence | Insufficient evidence |
|---|---|---|
| Confirmed | Site-specific evidence explicitly documents AI infrastructure, AI workloads, or a named AI deployment/project | Operator-wide AI strategy alone |
| Likely | Site-specific evidence strongly suggests AI relevance, but explicit confirmation is incomplete | Facility size alone |
| Mixed-use | Site-specific evidence supports both AI and non-AI use at the same site | Assuming all colocation sites are mixed-use |
| Unclassified | Evidence is insufficient, ambiguous, contradictory, or absent | Must not be interpreted as “not AI” |

**Evidence Strength**

```text
strong
moderate
limited
conflicting
```

**AI Deployment Stage**

```text
operational
announced
ai_ready_only
unknown
```

A facility can therefore be:

```text
Classification: Confirmed
AI stage: Announced
Facility status: Under construction
```

That does **not** mean AI workloads are already running there.

**Classification Rules**

1. Evaluate evidence at the facility level.
2. Do not inherit an operator’s AI positioning across all its sites.
3. Preserve the distinction between “AI-ready” and documented deployment.
4. Require a written rationale.
5. Record the supporting claims and source references.
6. Record the methodology version.
7. Have another reviewer inspect Confirmed and Mixed-use decisions.
8. Retain disagreements rather than silently overwriting them.
9. Reassess when new evidence materially changes the record.

**Reviewer Checklist**

```text
[ ] Is the facility specifically identified?
[ ] Is the statement about this site, not only the operator?
[ ] Does the evidence describe capability, plans, or actual operation?
[ ] Are AI and general-purpose workloads distinguished?
[ ] Is the source date recorded?
[ ] Are conflicting sources documented?
[ ] Does the rationale follow the current rubric?
```

**Optional AI Assistance**
A language model can later help extract candidate claims from documents.

Its output should remain a draft containing:

- Proposed field.
- Proposed value.
- Exact supporting passage.
- Source identifier.
- Relevant date.
- Extraction/model version.

It must not publish classifications, invent missing information, or treat instructions found inside source documents as executable instructions.

The project does not require training a custom AI model to deliver its main research contribution.

**7. Environmental Method**

**Water-Stress Interpretation**
The platform should say:

> This facility’s mapped location overlaps an area assigned this water-stress category by the selected Aqueduct dataset.

It should not say:

> This facility causes water scarcity.

WRI describes Aqueduct as a prioritisation and screening tool that should be supplemented by local investigation. Its baseline indicators are not live observations of conditions at an individual facility. ([wri.org](https://www.wri.org/research/aqueduct-40-updated-decision-relevant-global-water-risk-indicators?utm_source=openai))

**Aqueduct Fields**
Preserve the supplied forms of the indicator, including:

```text
bws_raw
bws_score
bws_cat
bws_label
```

The data dictionary distinguishes raw values, scores, categories, and labels. Do not treat them as interchangeable. ([raw.githubusercontent.com](https://raw.githubusercontent.com/wri/Aqueduct40/master/data_dictionary_water-risk-atlas.md))

**Spatial Processing**

1. Validate and normalise facility geometry.
2. Validate source polygon geometry.
3. Confirm coordinate reference systems.
4. Match the facility to native-resolution environmental polygons.
5. Record all candidate matches.
6. Apply documented ambiguity rules.
7. Store the result against a specific facility version and dataset version.
8. Generate simplified display geometry separately.

Do not calculate analytical results using heavily simplified map polygons.

**Match Statuses**

```text
matched
no_data
outside_coverage
location_too_imprecise
boundary_ambiguous
multiple_matches
invalid_geometry
```

**Boundary Handling**
`ST_Covers` includes points on a polygon boundary, unlike strict interior-only logic. That is useful, but a point on a shared boundary can match multiple polygons. Detect those cases instead of taking the first result. ([postgis.net](https://postgis.net/docs/ST_Covers.html))

Example candidate-match query:

```sql
SELECT
    fv.id AS facility_version_id,
    COUNT(ra.id) AS candidate_count,
    ARRAY_AGG(ra.id)
        FILTER (WHERE ra.id IS NOT NULL) AS candidate_area_ids
FROM facility_versions AS fv
LEFT JOIN risk_areas AS ra
    ON ra.dataset_version_id = :dataset_version_id
   AND ST_Covers(ra.geom, fv.geom)
WHERE fv.id = ANY(:facility_version_ids)
GROUP BY fv.id;
```

**Location Uncertainty**
Store location precision explicitly:

```text
verified_site
approximate_site
locality_only
city_only
unknown
```

Also store a documented uncertainty radius where one is supportable.

- Precise site locations can receive a point-based assessment.
- Approximate locations may require checking all intersecting polygons.
- City-only records should not receive a precise site-level risk label.
- Do not silently assign the nearest basin when a point fails to match.

**CEEW Joins**
Match CEEW values to the administrative geography used by that index.

If a current district is a subdivision of an older district:

- Retain the original district identifier.
- Document the relationship.
- Label inherited context as parent-district context.
- Do not present it as a newly measured score for the current district.

**No Composite Score**
For the initial release, keep water stress and climate vulnerability separate.

Do not create an arbitrary formula such as:

```text
overall_risk = 0.6 * water_stress + 0.4 * climate_vulnerability
```

A combined score would require its own justified methodology, validation, sensitivity analysis, and explanation.

**Exposure Metric**
For a selected group of facilities:

```text
High-stress share =
  assessable facilities in High or Extremely High categories
  ---------------------------------------------------------
  all facilities with valid, eligible water-stress assessments
```

Show the numerator, denominator, and excluded-record count.

**Capacity Rules**

- Separate operational, under-construction, and proposed capacity.
- Separate IT load from total facility power or grid connection capacity.
- Do not sum campus totals and their component phases.
- Do not turn MW into annual electricity consumption without a separate, explicit model.
- Do not infer water consumption from capacity alone.
- Unknown capacity must not be represented as zero.

**Discovery**
Start with OSM and manually collected primary sources.

Example Overpass query for a **research bounding box around Mumbai**, not an official hub definition:

```text
[out:json][timeout:60][bbox:18.8,72.7,19.4,73.4];

(
  nwr["telecom"="data_center"];
  nwr["building"="data_center"];
  nwr["industrial"="data_centre"];
  nwr["construction:telecom"="data_center"];
  nwr["proposed:telecom"="data_center"];
);

out meta geom;
```

Overpass supports bounding-box queries and geometry output. Its `out center` option returns a bounding-box centre, which is not guaranteed to lie inside a polygon; do not automatically treat it as a verified site coordinate. ([wiki.openstreetmap.org](https://wiki.openstreetmap.org/wiki/OverpassQL))

**Source Archiving**
Store:

- Source reference.
- Retrieval time.
- Publication time if known.
- Content checksum.
- Relevant page or section.
- Permitted excerpt.
- Parsing status.
- Rights information.

Store full documents only where permitted. A public citation does not require republishing a full article.

**Deduplication**
Use a combination of:

- Operator aliases.
- Facility/site codes.
- Address similarity.
- Geographic proximity.
- Campus and phase relationships.
- Shared source references.

Proximity should create a review suggestion, not automatically merge records.

**Normalisation**
Standardise:

```text
operator names
facility aliases
lifecycle statuses
dates and date precision
capacity units
capacity basis
coordinate reference systems
administrative identifiers
source types
```

**Review**
Each candidate should end in:

```text
accepted
rejected
duplicate
needs_more_evidence
out_of_scope
```

**Idempotency**
Running the same import twice should not create duplicate candidates, claims, or assessments.

Use stable upstream IDs and content/version checksums as idempotency keys.

**Publishing**
The publication job should:

1. Validate all selected records.
2. Verify evidence and rights requirements.
3. Pin dataset versions.
4. Compute aggregates.
5. Create permitted exports.
6. Generate a manifest and checksums.
7. Publish the release atomically.
8. Update the “latest release” pointer only after success.

**13. Security And Operations**

**Roles**

| Role | Permissions |
|---|---|
| Public visitor | Read published data and submit corrections |
| Contributor | Prepare drafts if contributor accounts are enabled |
| Reviewer | Review and approve content |
| Administrator | Manage users, imports, and releases |

Public users should not need an account to explore or download permitted public releases.

**Authentication**
Use an established identity provider for admin authentication.

Require:

- Server-side authorisation on every restricted route.
- MFA for privileged accounts.
- Secure, HttpOnly cookies if using cookie sessions.
- CSRF protection for cookie-authenticated mutations.
- No long-lived privileged tokens in browser local storage.
- Audit logs for approval and publication actions.

Cookie-authenticated application design should follow established CSRF protections rather than relying only on hidden admin URLs or frontend checks. ([cheatsheetseries.owasp.org](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html))

**Untrusted Inputs**
Source URLs and uploaded documents require particular care.

- Do not automatically fetch arbitrary URLs submitted by the public.
- Use an isolated ingestion environment.
- Block internal, loopback, link-local, and cloud metadata destinations.
- Validate DNS resolution and redirects.
- Set response-size and execution-time limits.
- Sandbox document parsing.
- Render excerpts as sanitised text.
- Do not execute document scripts or macros.

These controls address the SSRF risks inherent in server-side URL fetching. ([cheatsheetseries.owasp.org](https://cheatsheetseries.owasp.org/cheatsheets/Server_Side_Request_Forgery_Prevention_Cheat_Sheet.html))

**Other Requirements**

- Parameterised database queries.
- Rate limits on search, exports, and corrections.
- CSV formula-injection protection.
- Restricted file types and upload sizes.
- Secrets outside Git.
- Dependency and container vulnerability scanning.
- No public database port.
- Private correction submitter contact details.
- Data-retention rules for submitted personal information.

**Responsible Publication**
Exclude non-public operational details such as security layouts, internal network topology, access arrangements, and precise infrastructure dependencies that are unnecessary for this research.

Provide a correction and removal-review process for sensitive or disputed records.

**14. Research Evaluation**

**Research Questions**

1. How reliably can public evidence support facility-level AI classification?
2. What share of assessable facilities overlaps high water-stress areas?
3. How does documented facility density vary with district-level water-stress context?
4. How do results change when uncertain locations and Likely classifications are excluded?
5. Which information gaps most limit interpretation?

A statistically insignificant result is still a valid research outcome.

**Classification Evaluation**

1. Write the rubric before evaluating the full dataset.
2. Select a stratified sample across hubs, statuses, and evidence categories.
3. Have two reviewers label the sample independently.
4. Record disagreements.
5. Adjudicate a reference set.
6. Freeze the reference set for evaluation.
7. Report class-level results and uncertainty.

Suggested measures:

| Measure | Purpose |
|---|---|
| Agreement percentage | Simple reviewer consistency |
| Cohen’s kappa | Agreement beyond chance |
| Per-class precision and recall | Identify which labels are unreliable |
| Macro F1 | Avoid majority-class dominance |
| Confirmed-class precision | Detect overstatement of AI evidence |
| Unclassified share | Make evidence gaps visible |

Use planning targets such as high Confirmed precision, but do not claim a target was achieved without a sufficient test sample and reported uncertainty.

**Spatial Analysis**
Do not calculate a correlation from only five hub-level observations and present it as strong national evidence.

Define a district-level study frame covering the selected hub regions.

For district \(d\):

\[
D_d =
\frac{\text{reviewed sites in district }d}
{\text{district area in km}^2}
\times 1000
\]

This gives documented sites per 1,000 square kilometres.

Calculate area using an appropriate projected CRS or geodesic area, not square degrees. PostGIS distinguishes planar geometry area from geography-based area calculations. ([postgis.net](https://postgis.net/docs/ST_Area.html))

A possible project-derived water-context statistic is:

\[
H_d =
\frac{\text{validly assessed district area in high/extreme stress}}
{\text{district area with valid water-stress data}}
\]

Clearly label this as an **observatory-derived area share**, not a native WRI district score.

**Analysis Procedure**

1. Freeze the facility and environmental releases.
2. Predefine eligible districts.
3. Record research coverage and search effort.
4. Calculate site density.
5. Calculate district water-context statistics.
6. Plot density against water context.
7. Report descriptive Spearman correlation.
8. Check spatial dependence and sensitivity.
9. Repeat excluding approximate locations.
10. Repeat with narrower AI-evidence subsets.

Do not blindly use the default correlation p-value. SciPy’s documentation cautions about the accuracy of its Spearman p-value for smaller samples; spatial dependence introduces an additional reason to avoid treating districts as automatically independent. If formal inference is attempted, document a defensible spatial resampling or modelling approach. ([docs.scipy.org](https://docs.scipy.org/doc/scipy/reference/generated/scipy.stats.spearmanr.html))

**Mandatory Limitations**

- The inventory is not a census.
- Research coverage can vary between hubs.
- Unclassified does not mean non-AI.
- Unknown capacity is missing data.
- District vulnerability is not a site-specific engineering assessment.
- A basin overlapping the site may not be the facility’s actual water-supply catchment.
- Data-source dates do not all match.
- Correlation does not establish causation.
- Adding previously unknown older sites is a coverage change, not necessarily infrastructure growth.

**15. Quality Requirements**

All numbers below are **acceptance targets**, not measured performance claims.

| Area | Target |
|---|---|
| Public evidence | Every material published claim has evidence or an explicit unknown state |
| AI review | Every Confirmed/Mixed-use record receives a second review |
| Release integrity | Every release has a reproducible manifest |
| Spatial integrity | Every attempted assessment records a result or explicit failure reason |
| API performance | Common filtered reads below 500 ms p95 under the defined staging test |
| Frontend | Target LCP at or below 2.5 seconds at the 75th percentile |
| Interaction | Filters provide immediate feedback and do not freeze the map |
| Mobile | Core flows work at 360 CSS pixels |
| Accessibility | WCAG 2.2 AA target |
| Recovery | Backups are tested through actual restoration |

Measure performance against a documented device/network profile and dataset size.

**Required Tests**

| Test | Expected result |
|---|---|
| Import the same source twice | No duplicate records |
| Two announcements describe one expansion | One site with separate phase/history evidence |
| A facility has no capacity disclosure | Display “Unknown”, not zero |
| Campus total and phase capacities coexist | Aggregate does not double-count |
| A point lies on two polygon boundaries | Assessment is flagged as ambiguous |
| A coordinate is only city-level | No false precise site assessment |
| A risk source contains a missing-data code | Preserve a typed missing state |
| A draft is requested publicly | Not returned |
| Filters are changed | Map, table, chart, and export populations agree |
| A new release is published | Previous release remains unchanged |
| A source excerpt contains HTML/script | Rendered safely |
| A correction includes an internal-network URL | Not fetched |
| WebGL fails | Table and profiles remain usable |
| A restricted dataset is selected for export | Export is blocked or appropriately separated |
| A backup is restored | Application can read the restored release |

**Usability Study**
Test with approximately 5-8 participants across your intended users.

Give them tasks such as:

| Slow maps | Lightweight features, simplified display layers, later vector tiles |
| Overengineering | One API, one spatial database, scheduled jobs first |
| Misleading research conclusions | Explicit denominators, sensitivity tests, coverage limits |
